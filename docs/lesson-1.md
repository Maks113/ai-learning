Первую неделю сделаем фундаментальной и без LangChain/LangGraph. Задача — почувствовать разницу между обычным API и недетерминированным компонентом, а заодно построить слой, который потом не придётся выбрасывать.

Проект: AI Support Ticket Analyzer

На вход приложение получает произвольное сообщение пользователя:

После смены номера телефона я больше не могу войти.
При восстановлении пароля SMS приходит на старый номер.
Нужно срочно восстановить доступ.

LLM должна превратить его в строго типизированный объект примерно такого смысла:

interface TicketAnalysis {
category: TicketCategory;
priority: TicketPriority;
summary: string;
language: string;
requiresHuman: boolean;
}

Но конкретный prompt, JSON Schema и способ валидации — часть задания.

Архитектурное ограничение

Приложение не должно зависеть напрямую от конкретной LLM.

Нужна граница вида:

                 ┌──────────────────┐
HTTP / CLI ─────►│ TicketAnalyzer   │
└────────┬─────────┘
│
▼
┌─────────────┐
│ LLMProvider │
└──────┬──────┘
│
┌───────────┴──────────┐
▼                      ▼
OpenAIProvider        LocalProvider
│
▼
local model

Локальную модель можешь запускать через OpenAI-compatible endpoint. Поэтому постарайся сделать так, чтобы переключение:

LLM_PROVIDER=openai

на

LLM_PROVIDER=local

не затрагивало бизнес-логику.

Обязательные требования

Используй TypeScript. HTTP API можно сделать на NestJS/Fastify/Express — здесь выбор не принципиален.

Реализуй POST /tickets/analyze, принимающий:

{
"text": "..."
}

Ответ должен быть строго типизирован. Минимально нужны категории вроде authentication, billing, technical, other и несколько уровней priority.

Обязательны также: интерфейс LLMProvider; минимум две реализации — облачная и OpenAI-compatible локальная; structured output вместо просьбы «ответь JSON»; runtime-валидация ответа модели через Zod/Ajv/аналог; корректная обработка malformed/invalid model response; timeout; конфигурация через environment; .env.example; отсутствие API keys в репозитории.

Очень важное ограничение: не исправляй плохой JSON регулярками и не доверяй TypeScript cast вроде response as TicketAnalysis.

Хочу, чтобы в коде явно существовала граница:

untrusted LLM output
│
▼
validation
│
valid?
/    \
yes     no
│       │
domain     error
Эксперимент

Это обязательная часть задания.

Подготовь минимум 20 разных сообщений: нормальные, очень короткие, длинные, неоднозначные, на русском/английском, с несколькими проблемами одновременно.

Запусти их через обе модели.

Получится что-то вроде:

                 Cloud    Local

valid schema       ?        ?
correct category   ?        ?
avg latency         ?        ?
failures            ?        ?

Не нужно строить сложную систему evals — до неё мы дойдём отдельно. Сейчас можно оценить correct category вручную.

Мне важнее, чтобы ты увидел поведение двух моделей на одинаковом контракте.

⭐ Дополнительные задачи

Если основное закончишь быстро, добавь streaming для отдельного обычного chat endpoint и посмотри, почему streaming почти ничего не даёт конкретно для нашего structured-output endpoint.

Ещё интереснее: добавь retry только для определённых типов ошибок LLM и подумай, какие ошибки повторять безопасно, а какие бессмысленно.

И третий вариант — посчитай приблизительное количество input/output tokens и стоимость запроса для облачной модели.

Не обязательно делать все три.

Тесты

Минимум хочу увидеть unit-тесты вокруг границы LLM.

Например:

invalid JSON/schema
unknown category
missing field

Саму реальную модель в unit tests вызывать не нужно.

Сделай:

FakeLLMProvider

или mock реализации интерфейса.

Это заодно покажет, насколько удачно ты выбрал abstraction boundary.

Критерий готовности

Задание считается выполненным, если я могу клонировать репозиторий, выполнить описанные в README команды, отправить текст в /tickets/analyze и получить либо валидный TicketAnalysis, либо контролируемую ошибку — но никогда произвольный ответ модели.

При переключении provider бизнес-код не должен изменяться. Тесты должны проходить без настоящего API key. В README должны быть результаты эксперимента с двумя моделями и твои архитектурные выводы.
